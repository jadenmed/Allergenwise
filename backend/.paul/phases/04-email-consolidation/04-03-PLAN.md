<objective>
## Goal
Convert the remaining `await sendEmail(...)` call sites for non-critical, already-fault-tolerant emails into true fire-and-forget calls (`sendEmail(...).catch(err => console.error(...))`, not awaited), matching the pattern `stripe/webhook`'s `sendWelcomeAdminEmail(...)` already uses. Take ~300-800ms of Resend network latency off each of these routes' response time.

## Purpose
Audit item B4 (Part A #3). `sendEmail()` never throws (04-01/04-02 established this is now the ONLY send path), so anywhere the response doesn't semantically depend on email delivery succeeding, awaiting it before returning is pure wasted latency. The genuinely fault-tolerant sites are the target; sites that currently use email failure as a real signal to the caller are called out below and get a decision, not a silent behavior change.

## Output
- `exam/submit`, `submissions/create`, `account/me/request-deletion`: email call no longer blocks the response.
- `invites/send`: gains a `.catch()` it currently lacks, and stops awaiting.
- `invites/remind`, `invites/[id]/resend`: **behavior change** — currently return HTTP 500 to the caller when email delivery fails; this plan makes them fire-and-forget (matching the audit's stated intent), so a Resend outage no longer fails the admin's reminder/resend action. Flagged explicitly for human-verify below since it changes an existing API contract, not just timing.
</objective>

  <context>
    Research during planning found these 2 routes do NOT match the audit's blanket claim that invite emails are "already .catch-guarded, non-fatal." Today: `invites/remind` and `invites/[id]/resend` await the send with no try/catch and explicitly return `NextResponse.json({error: ...}, {status: 500})` when the email fails — meaning an admin clicking "remind" or "resend" today gets a visible error if Resend is down, which is arguably useful signal (retry now) but also means the whole B4 latency win doesn't apply to these two routes without a behavior change. `invites/[id]/resend` is a sharper case: by the time the email send runs, the invite token has ALREADY been rotated in the DB — a 500 here is misleading (the mutation succeeded, only the email failed), which argues FOR fire-and-forget.
  </context>
  <options>
    <option id="fire-and-forget">
      <name>Convert both to fire-and-forget (recommended)</name>
      <pros>Matches B4's stated intent and the stripe/webhook reference pattern; fixes the misleading "500 but the mutation already succeeded" case in invites/[id]/resend; consistent behavior across all invite-email routes (send/remind/resend all become fire-and-forget together, matching 04-01's already-migrated invites/send once Task 2 lands)</pros>
      <cons>Admin no longer gets an immediate error signal if Resend is down when clicking remind/resend — they'd need to notice the email never arrived. Mitigated by the fact the underlying action (reminder sent, token rotated) did succeed; the admin can always retry the remind/resend action itself if the employee reports not receiving it</cons>

      <pros>No API contract change, zero risk to this plan's behavior-preserving mandate</pros>
