<objective>
## Goal
Replace one-insert-per-row `activity_events` writes inside loops with a single batched `insert([...])` call per handler/cron invocation. Behavior-preserving: same events, same payloads, same insertion order. Preserve the `activity_events_certificate_id_idx` partial index's usefulness by keeping `ORDER BY created_at` semantics intact — batched rows must not collapse onto one `now()` timestamp, since a single multi-row INSERT evaluates `now()` once per statement in Postgres.

## Purpose
Audit Part A #2 (narrow). `cert-event-handlers.ts` (Stripe webhook hot path, 6 loops) and 3 cron routes fire N separate round-trips for events emitted in a single invocation. Batching to 1 round-trip per invocation is a mechanical win with no data-shape change.

<acceptance_criteria>

## AC-1: Same events, same payloads, single round-trip
```gherkin
Given a handler invocation that previously fired N separate activity_events inserts in a loop
When the handler runs after batching
Then exactly one `activity_events` insert() call is made per invocation (per logically-atomic group)
And the set of {type, payload} tuples written is byte-identical to the pre-batch behavior
```

## AC-2: Event ordering preserved
```gherkin
Given a batched insert of N rows in one statement
When the rows are queried via `ORDER BY created_at` (the canonical cert-history query)
Then the returned order matches the original loop iteration order
```
Implementation note: Postgres evaluates `now()` once per statement, so relying on the `created_at default now()` column default across a multi-row insert would give every row in the batch an IDENTICAL timestamp and an UNDEFINED tie-break order. Each row must be stamped with an explicit, strictly-increasing `created_at` (e.g. base timestamp + monotonic offset in milliseconds, one per row in iteration order) before the batched insert.

## AC-3: Partial index untouched, still selective
```gherkin
Given the `activity_events_certificate_id_idx` partial index (`payload->>'certificate_id' where payload ? 'certificate_id'`)
When batched rows are inserted
Then rows that previously carried `certificate_id` in payload still carry it (index remains populated identically)
And rows that never carried it (e.g. subscription_expired, dispute_funds_*) still don't (index stays equally selective)
```

## AC-4: Non-fatal insert-error handling preserved
```gherkin
Given `activity_events` insert failures are currently non-fatal (logged, not thrown) in every touched site
When the insert is batched
Then a failed batched insert is still non-fatal (logged, handler continues / cron continues to next phase) — never blocks the cert state UPDATE or the cron's core work
```

## AC-5: Typecheck + lint + build + tests green
```gherkin
Given the changes are applied
When npx tsc --noEmit, lint, build, and the audit-trail unit/integration suite run
Then there are no new errors and all previously-passing tests still pass
```
